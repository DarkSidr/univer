# Итоговый отчет по продукту

## Проект

Персональный менеджер задач (Todo List) с категориями.

## Выполненные лабораторные работы

| Лабораторная | Результат |
| --- | --- |
| №1 | Проведено исследование проблемы, CustDev, JTBD, конкурентный анализ и сформулированы гипотезы |
| №2 | Подготовлены AS-IS/TO-BE диаграммы, User Stories, Use Case, wireframes и backlog |
| №3 | Реализован MVP на C#/.NET 8, добавлено JSON-хранилище и аналитическое логирование |
| №4 | Проведен A/B эксперимент поиска, добавлена оценка важности задачи и выполнен рефакторинг |
| №5 | Добавлены наблюдаемость, метрики, стресс-тест, расчет экономики и итоговый анализ |

## Итоговая функциональность

- CRUD для задач.
- Категории "Работа", "Учеба", "Личное".
- Название, описание, дедлайн, статус выполнения.
- Локальное хранение данных в JSON.
- Структурированное логирование событий в JSON Lines.
- Поиск задач в режимах Contains и Regex.
- A/B benchmark поиска.
- Автоматическая оценка важности задачи.
- Стресс-тест через CLI-команду `--stress-test`.
- Просмотр простых метрик в консоли.

## Наблюдаемость

В проект добавлено структурированное логирование в файл `analytics.log`. Каждое событие записывается отдельной JSON-строкой.

Примеры событий:

- `app_started`;
- `task_created`;
- `task_completed`;
- `task_search_used`;
- `search_ab_test_completed`;
- `operation_measured`;
- `stress_test_completed`;
- `metrics_viewed`.

Такой формат можно импортировать в аналитические системы или обрабатывать скриптами.

## Стресс-тест

Для симуляции нагрузки добавлена команда:

```bash
dotnet run --project src/TodoList.Console/TodoList.Console.csproj -- --stress-test 1000
```

Команда:

1. Генерирует указанное количество задач.
2. Сохраняет их в JSON.
3. Измеряет время генерации.
4. Сравнивает поиск Contains и Regex.
5. Измеряет фильтрацию по категории.
6. Записывает результат в `analytics.log`.

## Производительность

По результатам экспериментов:

- поиск через `Contains` быстрее и проще для пользовательского сценария;
- `Regex` полезен только для расширенного поиска по шаблонам;
- фильтрация по категории на локальном списке выполняется быстро;
- основной риск производительности для текущей реализации - частая запись всего JSON-файла при большом количестве задач.

Фактический стресс-тест на 1000 задач:

| Метрика | Значение |
| --- | --- |
| Время генерации 1000 задач | 1081.356 мс |
| Поиск Contains | 4.292 мс |
| Поиск Regex | 27.542 мс |
| Фильтрация категории | 0.045 мс |

Вывод по стресс-тесту: на 1000 задач деградация поиска и фильтрации не критична. Наиболее заметная операция - массовая генерация с сохранением JSON после каждой задачи.

Для следующей версии стоит рассмотреть:

- пакетную запись при массовой генерации;
- хранение в SQLite;
- индексацию по категории и статусу;
- отдельный режим импорта большого количества задач.

## Проверка гипотез

### Гипотеза 1

Фиксированные категории помогают быстрее находить задачи.

Статус: частично подтверждена.

Основание: в продукте реализованы категории и событие `category_filtered`, по которому можно измерять частоту использования фильтра. Для полного подтверждения нужны реальные пользовательские данные за период тестирования.

### Гипотеза 2

Минимальное создание задачи только по названию повышает частоту добавления мелких задач.

Статус: частично подтверждена.

Основание: описание и дедлайн необязательны, события `task_created` содержат поля `has_description` и `has_deadline`. Это позволяет проверить, сколько задач создается с минимальным заполнением.

### Гипотеза 3

Локальное JSON-хранилище без регистрации делает продукт проще для личного использования.

Статус: частично подтверждена.

Основание: приложение работает локально, без регистрации и внешних сервисов. Повторные запуски можно оценивать через `app_started`.

## Итоговый вывод

Прототип закрывает базовую проблему пользователя: быстро записать задачу, разложить ее по категории, сохранить локально и контролировать выполнение. Для учебного MVP выбранная архитектура достаточна. Для развития продукта дальше наиболее важны синхронизация, напоминания, улучшение хранения данных и сбор реальных пользовательских метрик.
