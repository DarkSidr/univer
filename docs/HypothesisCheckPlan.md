# Лабораторная работа №3. План проверки гипотез

## Проект

Персональный менеджер задач (Todo List) с категориями.

## Цель

Описать, как с помощью событий из лог-файла MVP можно проверить гипотезы, сформулированные в лабораторной работе №1.

## Логирование в MVP

Приложение записывает события в файл `analytics.log` в формате JSON Lines. Каждая строка является отдельным JSON-объектом.

Пример события:

```json
{"event":"task_created","user":"local_user","time":"2026-05-07T17:10:00.0000000+05:00","task_id":1,"category_id":2,"has_description":true,"has_deadline":true,"is_completed":false}
```

## События

| Событие | Когда записывается | Зачем нужно |
| --- | --- | --- |
| `app_started` | При запуске приложения | Оценить повторное использование приложения |
| `task_created` | При создании задачи | Оценить частоту добавления задач |
| `tasks_listed` | При просмотре общего списка | Оценить востребованность общего списка |
| `category_filtered` | При просмотре задач по категории | Проверить полезность категорий |
| `task_updated` | При редактировании задачи | Понять, насколько часто пользователи уточняют данные |
| `task_completed` | При отметке выполнения | Оценить использование статуса выполнения |
| `task_deleted` | При удалении задачи | Оценить очистку неактуальных задач |
| `validation_failed` | При ошибках в обязательных полях | Найти проблемы интерфейса и ввода |

## Гипотеза 1

Если в приложении будут фиксированные категории "Работа", "Учеба", "Личное", то пользователи быстрее будут находить нужные задачи и реже смешивать разные контексты.

### Метрики

- Количество событий `category_filtered`.
- Доля просмотров по категории среди всех просмотров списков:

```text
category_filtered / (category_filtered + tasks_listed)
```

### Критерий подтверждения

Гипотеза считается подтвержденной, если за тестовый период не менее 40% просмотров задач выполняется через фильтр по категории.

### Как проверить

1. Дать пользователям MVP на 5-7 дней.
2. Собрать файл `analytics.log`.
3. Посчитать события `category_filtered` и `tasks_listed`.
4. Сравнить долю фильтрации с порогом 40%.

## Гипотеза 2

Если создание задачи будет требовать только название, а описание и дедлайн будут необязательными, то пользователи будут чаще добавлять мелкие задачи сразу после их появления.

### Метрики

- Количество событий `task_created`.
- Доля задач без описания:

```text
task_created where has_description = false / task_created
```

- Доля задач без дедлайна:

```text
task_created where has_deadline = false / task_created
```

### Критерий подтверждения

Гипотеза считается подтвержденной, если за тестовый период пользователь создает не менее 10 задач, а не менее 30% из них создаются без описания или без дедлайна.

### Как проверить

1. Собрать события `task_created`.
2. Для каждого события проверить поля `has_description` и `has_deadline`.
3. Посчитать долю быстро созданных задач с минимальным заполнением.

## Гипотеза 3

Если данные будут сохраняться локально в JSON без регистрации и настройки синхронизации, то пользователи, которым нужен простой личный инструмент, будут воспринимать приложение как более легкое и понятное.

### Метрики

- Количество повторных запусков `app_started`.
- Количество успешных действий после запуска: `task_created`, `task_completed`, `task_updated`.
- Количество ошибок `validation_failed`.

### Критерий подтверждения

Гипотеза считается подтвержденной, если пользователь запускает приложение повторно не менее 3 раз за тестовый период и после запусков выполняет основные действия без большого числа ошибок ввода.

Дополнительный критерий:

```text
validation_failed / (task_created + task_updated + task_completed) < 0.3
```

## План эксперимента

1. Передать MVP 2-3 пользователям из целевой группы.
2. Попросить использовать приложение для учебных, рабочих и личных задач в течение недели.
3. Не объяснять подробно интерфейс, чтобы проверить понятность консольного меню.
4. После теста собрать `analytics.log`.
5. Посчитать события вручную или с помощью простого скрипта.
6. Сравнить показатели с критериями подтверждения.
7. Зафиксировать вывод: гипотеза подтверждена, частично подтверждена или опровергнута.
